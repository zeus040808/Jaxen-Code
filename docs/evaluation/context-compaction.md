# 上下文压缩：模块评测

测 `ContextManager` 的三档压缩（轻压缩 / 摘要 / 兜底裁剪）在各种历史形状下是否守住不变量。用假模型，零成本，
结果可复现；进 pytest。机制本身见 [上下文工程](../architecture/context-engineering.md)。

```bash
.venv/bin/python scripts/eval/run_context_compaction.py   # 结果写入 artifacts/deterministic/context-compaction-v1.json
```

代码：`hh_agent_pro/evaluation/context_compaction.py`，门禁测试 `tests/test_context_compaction_eval.py`。

## 判分：每次请求的不变量

| 不变量 | 含义 |
|---|---|
| within_budget | 估算 token ≤ 预算 |
| protocol | 每个工具调用紧跟它的全部结果，没有孤立的 tool_call id；thinking 模型的思考内容原样回传 |
| goal_present | 用户请求**全文**还在（消息里或提醒里） |
| latest_intact | 最新一条工具结果原文还在 |
| system_stable | system 不变（前缀缓存） |
| history_intact | session 里的完整历史没被删改（断点恢复、会话检索靠它） |

另外在历史里埋"标记事实"（`FACT: old-0` 最早、`FACT: recent-N` 最新），检查压缩后还在不在。
摘要由假模型来写：把 `FACT:` 行原样抄进摘要，相当于忠实的摘要器。测的是"摘要能否正确进入后续请求"，
**不测摘要质量**（要真实模型）。

## 两部分

- **A：直接调用 `prepare()`**。造出历史后把预算设成"当前请求恰好占 X%"，精确落在某个档位。和真实运行一样先
  `task_state.begin()`，提醒里会带任务目标。
- **B：真实 agent 跑长任务**。复用[故障注入](fault-injection.md)的假服务器：16 次大文件读取 + 修复，预算 7000 token；
  假服务器回答摘要请求，并逐个检查 agent 发出的每一次请求。

## 结果（2026-11-05）

14 个场景全部通过（修复一个问题后）。

| 场景 | 档位 | 压缩比 | 事实保留 |
|---|---|---|---|
| under_threshold（50%） | 不压缩 | — | 最早、最新都在 |
| light_band（70%） | 轻压缩 | 55% | 最新在，最早被清理（按设计：提示模型需要时重跑工具） |
| summary_band（90%） | 摘要 | 65% | 最早的进了摘要，最新原文在 |
| summary_twice | 摘要 ×2 | 66% | 第一轮的事实穿过两次摘要仍在 |
| summary_fails_then_trim | 轻压缩 + 裁剪 | 68% | 最新在，目标在 |
| summary_disabled_then_trim | 轻压缩 + 裁剪 | 68% | 同上 |
| long_request_then_trim | 轻压缩 + 裁剪 | 69% | **请求全文在**（修复前不在，见下） |
| huge_recent_outputs | 摘要 | 69% | 最近几条本身很大时仍守住预算 |
| parallel_calls | 摘要 | 67% | 一次多个工具调用不被拆开 |
| reasoning_replay | 摘要 | 65% | 保留的工具调用都带思考内容 |
| calibration_triggers_earlier | 摘要 | 42% | 真实用量是估算 2 倍时，估算占 50% 也进入摘要 |
| B long_task_compacts_and_finishes | 摘要 ×2 | — | 20 次请求全部满足不变量，任务完成 |
| B long_task_summary_fails | 轻压缩、裁剪交替 | — | 22 次请求全部满足不变量，任务完成 |
| B huge_command_output | — | — | 4 万多字符的命令输出：头尾的事实在，中间的被截掉 |

### 发现的问题

| 问题 | 状态 |
|---|---|
| **兜底裁剪丢掉长请求的后半段**：裁剪从最旧的消息开始丢，用户请求最先被丢；提醒里的任务目标只留前 1000 字符。请求超过 1000 字符（SWE-bench 的 issue 常见）时，后半段在裁剪后彻底消失。只在摘要失败或关闭时才会走到裁剪 | **已修**：裁剪后请求全文不在了，就留出位置重新裁一次，把全文放回末尾提醒（`context_manager.prepare`）。用评测证实：把 `prepare()` 换回提交前的版本，这个场景失败；修复后通过。回归测试 `tests/test_context_manager.py::test_trim_fallback_keeps_a_long_user_request_in_full` |
| **摘要持续失败时每轮都重试**：B 部分 22 次请求里另有 13 次失败的摘要请求。假服务器返回 400，立即失败；真实 5xx 故障时，每次摘要都会先走 provider 的 6 次退避重试 | 观察到，**待定**：可以在一次运行内摘要失败后不再尝试，直接轻压缩 + 裁剪 |

### 搭评测时踩的坑

- 只用 `prepare()` 而不开始任务，提醒里没有任务目标，会误以为短请求也会丢；真实运行里短请求靠任务目标保住了。
  所以 A 部分改成先 `task_state.begin()`。
- 在 `json.dumps(messages)` 里找请求原文会因为换行被转义而找不到，改为比对消息原文。
- "最早的事实"要取第一条：轻压缩保留最近 8 条工具结果，更早但仍在这 8 条里的不会被清理。

## 真实模型的摘要保真度（2026-11-05）

上面用的是"忠实的假摘要器"，只证明流程对。这里用真实的 deepseek-flash 和现有摘要提示词，压缩真实的 SWE-bench 对话：

```bash
.venv/bin/python scripts/eval/run_summary_fidelity.py   # 调用真实模型，14 段约 13.6 万输入 token，花费几毛钱
```

- 样本：6 份完整对话记录（transcript），每份在历史的 50% 和 100% 处各截一段，共 14 段；跑了 2 遍，共 28 次摘要。
- 请求和 `ContextManager._summarize()` 完全一样（同一提示词、每条最多 4000 字符、最多输出 4096 token）。
- 标准答案用程序从历史里抽：改过的文件、跑过的测试文件 / 模块、失败输出里的异常类型、读过的文件；
  另查摘要里出现、历史里从没出现过的 `.py` 路径（编造）。代码 `hh_agent_pro/evaluation/summary_fidelity.py`。

| 输出类型 | 次数 | 现在的代码怎么处理 |
|---|---|---|
| 合格的 5 段摘要 | 14（50%） | 接受 |
| **把对话接着往下写**（输出工具调用、假的工具结果和文件内容、DSML 协议） | 8（29%） | **当成摘要接受**：编造的内容会替换掉真实历史 |
| 空输出（思考用光 4096 个输出 token） | 4（14%） | 退回轻压缩 |
| 是摘要但写到一半被截断 | 2（7%） | 接受半截摘要 |

**合格的摘要质量很好**：改过的文件 9/9、测试目标 19/19、异常类型 3/3、读过的文件 31/31 全部保住；唯一一个"历史里没出现的路径"
是"下一步可以再跑 test_common.py"的建议，不算编造事实。

**问题在请求的组织方式和输出校验，不在提示词内容**：

1. 摘要请求的最后是原样的对话行（`[assistant tool call] …`、`[tool result] …`），模型容易把自己当成 agent 接着往下演。
2. deepseek-flash 是思考模型，4096 的输出上限常被思考用掉（截断的样本里思考 1.1 万–1.8 万字符）。
3. 代码只检查"非空"，接着演的对话和半截摘要都会被接受。

### 修复与复测（同日）

| 改动（`context_manager.py`） | 做法 |
|---|---|
| 请求组织 | 对话原文包进 `<conversation>…</conversation>`，结尾再给一次指令：对话已结束，不要接着写、不要调用工具，按 5 段写摘要（`build_summary_request`，评测脚本用同一个函数） |
| 输出上限 | `SUMMARY_MAX_TOKENS` 4096 → 16384（按实际用量计费） |
| 输出校验 | `summary_problem()`：被截断、缺第 1 或第 5 段、含工具调用协议标记的一律拒绝，走轻压缩 + 兜底裁剪，压缩记录里写 `summary_rejected` |
| 失败后不重试 | 同一次运行里摘要失败（请求出错或被拒绝）过一次就不再尝试；B 部分摘要失败场景从 13 次失败请求降到 1 次 |

复测（同样 14 段 × 2 遍）：

| | 修复前 | 修复后 |
|---|---|---|
| 合格并被接受 | 14/28（50%） | **28/28（100%）** |
| 把对话接着往下写 | 8 | 0 |
| 空输出 / 被截断 | 4 / 2 | 0 / 0 |
| 关键信息保留（合格的样本） | 全部 | 全部（改过的文件 12/12、测试目标 26/26、异常类型 6/6、读过的文件 60/60） |
| 输出 token 最大值 | 4096（顶格） | 7058（思考 2.4 万字符；旧上限下会被截断） |

唯一一个"历史里没出现的路径"仍是"下一步可以跑某个测试"的建议（后来 agent 确实跑了），不是编造事实。
回归测试：`tests/test_context_manager.py` 里接着写对话被拒、截断被拒、同一运行不重试、请求带标签和结尾指令 4 个。

## 和真实数据对照

SWE-bench 230 次运行里单次请求峰值：中位 2.6 万、p90 6.5 万、最大 7.66 万 token；轻压缩触发 5 次，摘要和裁剪 0 次。
所以摘要和裁剪这两档只在本评测里被检验过。命令输出的头尾截断（单条超过 3 万字符才截）在 12 份完整对话记录里只出现 3 次，
暂不需要"大结果存磁盘"。

## 局限

- 假摘要器不测摘要质量；真实模型的摘要质量见上一节。"压缩后模型还能不能做对"还没测。
- token 是估算值（用 API 返回的真实用量校准），预算判断有误差，阈值因此留了余量（60% / 80%）。
