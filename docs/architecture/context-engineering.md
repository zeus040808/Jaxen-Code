# 上下文工程

代码：`jaxen/context_manager.py`、`prompt_prefix.py`、`workspace.py`、`providers/base.py`。
旧的"8 分区字符配额"设计与它的问题见 [history/context-management-v1.md](../history/context-management-v1.md)。

## 1. 核心原则

**会话记录本身就是工作记忆：尽量原样保留，接近上限才压缩一次。**

旧设计每轮都把规则、记忆、证据、历史各自裁剪到固定字符数再拼起来。它来自 4k~8k 窗口的年代，
到了 1M 窗口就变成：窗口很大、实际只用 6%，项目说明还被截光，每轮内容都在变导致缓存命中很低。
现在的结构与 Claude Code、Codex 等主流 coding agent 一致。

## 2. 一次请求的三层

```
┌────────────────────────────────────────────────────────────────┐
│ system（整个 Session 不变，前缀缓存一直命中）                     │
│   身份 + 运行时信息 + 规则 + 工具策略                              │
│   + 项目指令：AGENTS.md / CLAUDE.md 完整注入，永不裁剪             │
│   + 环境快照：cwd、分支、git status、最近提交（会话开始时，不更新）   │
│   + 长期记忆快照 + skills 索引                                     │
├────────────────────────────────────────────────────────────────┤
│ messages（只追加）                                                │
│   [压缩摘要（若有）]                                               │
│   user / assistant(tool_calls) / tool / ... 原样转换               │
├────────────────────────────────────────────────────────────────┤
│ 最后一条 user 消息里的 <system-reminder>（每轮都变，放在最后）       │
│   断点恢复信息、任务进度与 todo、运行进度、运行时指令                │
└────────────────────────────────────────────────────────────────┘
```

| 设计点 | 理由 |
|---|---|
| 环境快照不随 git status 更新 | 每改一次文件 status 就变；放在 system 里实时更新会让整段缓存失效。快照里明确写着"不会更新"，模型需要时自己跑 git |
| README、pyproject 不预加载 | 普通文档模型需要时自己读；只有指令文档值得每轮都带 |
| 断点恢复信息放末尾 | 每次 checkpoint 都会变，放开头会破坏缓存（旧设计就放在 prefix 最前面） |
| 工具参数 schema 走原生 tools 字段 | system 里只写使用策略，不重复发送 |
| 历史最后一条是 user 时把提醒拼进去 | 避免连续两条 user 消息 |

## 3. 预算

预算按 **token** 计，并从模型窗口推导：

```
budget = min(working_budget, context_window − max_new_tokens − margin)
         working_budget = 128k（成本旋钮）   margin = max(4096, 窗口的 2%)
```

| 模型 | 窗口 | 来源 |
|---|---|---|
| deepseek-flash / deepseek-v4-pro | 1,048,576 | `providers/base.py` 的 `MODEL_LIMITS`（来自 DeepSeek `/models`） |
| 其他 OpenAI 兼容模型 | 默认 128,000 | `--context-window` 覆盖 |

**token 估算**：CJK 约 1 字 1 token，其余约 3.5 字符 1 token；每次 API 返回真实 `prompt_tokens`
后用 `observe_usage()` 校准（指数平滑，限制在 0.5~2 倍）。

**为什么不直接用满 1M**：每次请求都会把全部输入重新发一遍，费用随长度线性增长。128k 能覆盖大多数
真实任务（SWE-bench 简单题实测约 10 万 token），system 和早期历史又能命中缓存。

## 4. 压缩：只在接近预算时发生

| 级别 | 触发 | 做法 | 代价 |
|---|---|---|---|
| 轻压缩 | 估算 > 60% 预算 | 最近 8 条之外、超过 800 字符的旧工具结果换成"已清理，需要时重新运行工具"的占位符 | 不调用模型 |
| 摘要压缩 | 估算 > 80% 预算 | 最近的轮次（≤ 25% 预算）原样保留，更早的交给模型写成 5 段结构化摘要：请求与目标、决策与约束、读改过的文件、遇到的错误、当前状态与下一步 | 多一次模型调用，之后前缀重新稳定 |
| 兜底裁剪 | 仍 > 预算 | 从最旧的轮次开始丢弃，assistant 工具调用与其结果作为一个单元，不拆开；用户请求全文被裁掉时放回末尾提醒（2026-11-05） | — |

- 压缩状态存在 `session["context"]`（`summary`、`summary_upto`、`cleared`）。**历史本身不删**，
  `session_search` 与断点恢复仍能看到原文。
- 当前请求被摘要掉时，原文放回末尾提醒，目标不会丢。
- 摘要调用失败（网络、余额）不会让任务失败：退回轻压缩 + 兜底裁剪。
- 摘要输出要过校验（`summary_problem`）：被截断、缺第 1 或第 5 段、像工具调用协议的都拒绝，按失败处理；同一次运行失败过就不再尝试。
  摘要请求把对话原文包进 `<conversation>` 标签并在结尾重申指令，输出上限 16384（2026-11-05，真实模型评测发现 29% 的摘要是在接着演对话）。
- 每次压缩都会写一个 `context_reduction` 检查点，trace 里能看到前后 token 数。
- 开关：`context_reduction`（关掉则只在超出时兜底裁剪）、`context_summary`（关掉则不调用模型，
  结果确定，确定性评测用）。

## 5. 单条内容的上限

| 内容 | 上限 | 截断方式 |
|---|---|---|
| 工具结果 | 30,000 字符（约 8k token） | 头尾各留一半，中间标注省略了多少 |
| `read_file` | 同上 | 按整行截断，并提示 `start=N` 继续读，代码不走头尾截断 |
| 项目指令文档 | 单份 40,000 字符 | 只防异常大文件 |

上一轮请求是本轮前缀、提醒在最后、预算从窗口推导、预算内不压缩、轻压缩只清旧的大结果、
摘要压缩与请求回填、摘要失败的兜底、裁剪不拆工具对、usage 校准、运行中压缩留下检查点。
